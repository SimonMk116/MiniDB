# MiniDB

MiniDB is a C++20 learning project focused on building a small database engine from the storage layer upward. The current codebase implements the foundational page-store and buffer-management pieces needed before adding tables, records, and query execution.

## What is implemented

The project currently includes:

- fixed-size page storage using 8 KiB pages
- a file-backed `DiskManager` for reading, writing, and allocating pages
- a reusable page ID strategy via `FreeList` and `InMemoryFreeList`
- a clock-based buffer pool with pinning, dirty tracking, and flushing
- a `ClockReplacer` for second-chance eviction
- persistence and robustness tests for page allocation and buffer behavior

## Project goals

- keep the code understandable and teachable
- model the storage layer realistically enough to support later DBMS features
- separate page storage, eviction policy, and free-page logic cleanly
- validate behavior with focused unit-style tests

From the project root:

## Storage architecture

### Pages

Each page is a fixed byte buffer:

```cpp
constexpr std::size_t PAGE_SIZE = 8192;
```

The database file is treated as a contiguous array of pages, and page IDs correspond to offsets:

```text
offset = page_id * PAGE_SIZE
```

This simple scheme makes reads and writes predictable while leaving plenty of room to build higher-level record formats later.

### DiskManager

`DiskManager` owns the database file and provides the core file I/O operations:

- `readPage(page_id, page)`
- `writePage(page_id, page)`
- `allocatePage()`
- `freePage(page_id)`

It validates page IDs against the current file size, creates the database file if needed, and extends the file as new pages are allocated.

### FreeList strategy

`FreeList` is the strategy interface used to track reusable page IDs. The repository currently includes `InMemoryFreeList`, which maintains a in-memory stack of freed IDs and rejects duplicates.

This strategy is intentionally simple and is suitable for a single-process prototype, but it is not durable across process restarts. For the persistence design details, see [docs/free_list.md](docs/free_list.md).

### Buffer pool

`BufferPoolManager` caches pages in memory and decides which frame to evict when the cache is full. It supports:

- page pinning
- dirty-page tracking
- single-page flushes
- bulk flushing of all dirty pages
- clock-based eviction of unpinned frames

The buffer manager is intentionally single-threaded and follows a clear page lifecycle: fetch, pin, unpin, flush, and evict.

### Clock replacement

`ClockReplacer` implements a simple second-chance policy. Frames become eligible after they are unpinned, and referenced frames are given one extra chance before eviction.

## Current status

This project is currently in the storage foundation phase and has working tests around:

- page allocation and reuse
- database file persistence
- dirty-page flushing behavior
- buffer pool pinning and eviction logic

The next major milestones are:

1. record and tuple representation
2. heap table / slotted-page storage
3. schema and catalog metadata
4. SQL parsing and execution
5. transactions and recovery

## Notes

- page IDs use `uint32_t` and therefore have a finite addressable range
- the storage design is fixed to 8 KiB pages across the project
- the code is educational and intentionally small, clear, and easy to extend

## Contributing

Keep changes small and testable, prefer clear naming, and continue building the system in layers rather than adding broad, unrelated features all at once.
