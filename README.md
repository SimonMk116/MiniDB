# MiniDB

MiniDB is a small, learning-focused relational database project written in C++20. The current implementation focuses on the storage layer: fixed-size pages, a file-backed disk manager, a free-page allocator strategy, a clock-based buffer pool, and the tests that exercise the expected behavior.

## Project goals

- Build a minimal but realistic storage foundation for a database engine
- Keep each component small and understandable for study and extension
- Use page-oriented persistence and buffer management as the first building blocks
- Provide working tests around page allocation, persistence, dirty-write handling, and eviction

## Current status

The codebase already includes the foundational storage components:

- `Page`: 8 KiB fixed-size page abstraction
- `DiskManager`: file-backed page store with page allocation and free-page reuse
- `FreeList`: pluggable reusable page ID strategy
- `BufferPoolManager`: page cache with pinning, dirty tracking, flushing, and clock eviction
- `ClockReplacer`: second-chance replacement policy for unpinned frames

## Build and run

From the project root:

```bash
cmake -S . -B build
cmake --build build
```

Run the sample executable:

```bash
./build/minidb
```

Run the test executables directly or via CTest:

```bash
ctest --test-dir build --output-on-failure
```

## Storage architecture

### Page format

Each database page is a fixed-size byte array:

```cpp
constexpr std::size_t PAGE_SIZE = 8192;
```

The project treats the database file as a simple array of pages. Page IDs are sequential integers starting at 0, and each page is stored at a fixed offset:

```text
offset = page_id * PAGE_SIZE
```

This makes page lookup simple and predictable while leaving room for higher-level record formats later.

### Disk manager

`DiskManager` owns the database file and provides the basic I/O operations:

- `readPage(page_id, page)` reads a page from disk
- `writePage(page_id, page)` writes a page back to disk
- `allocatePage()` allocates a new page ID, extending the file when needed
- `freePage(page_id)` releases a page ID into a free-list strategy

The implementation validates page IDs against the current file size and rejects invalid accesses. It also keeps the page count in `next_page_id_` so new pages continue from the end of the file.

### Free list strategy

`FreeList` is an abstract strategy interface for tracking reusable page IDs. The current implementation uses `InMemoryFreeList`, which keeps a stack of available page IDs in memory. This is intentionally simple and is useful for a single-process prototype, but it is not durable across restarts.

For more detail, see [docs/free_list.md](docs/free_list.md).

### Buffer pool

`BufferPoolManager` caches pages in memory and uses a clock replacement policy to decide which unpinned frame to evict. Key behaviors:

- page frames can be pinned to prevent eviction
- dirty pages stay marked until they are flushed
- `flushPage()` writes a single dirty page to disk
- `flushAllPages()` writes every dirty resident page and rethrows the first disk error encountered
- failed writes do not silently corrupt the resident page state

The pool is intentionally single-threaded. It keeps a mapping from `page_id_t` to `frame_id_t`, a free-frame list, and a clock replacer that implements second-chance eviction.

### Clock replacer

`ClockReplacer` is a simple second-chance policy. Each frame starts as ineligible until it is unpinned, then it may be considered for eviction. If a referenced frame is encountered, its reference bit is cleared and it is skipped. This is a lightweight approximation of clock-based page replacement for educational use.

## Design notes and constraints

- Page IDs are currently `uint32_t`, so the database is bounded by the size of `page_id_t`
- The project uses a fixed 8 KiB page size throughout storage and buffer code
- Free-list implementations are intentionally separated from the storage file logic so different strategies can be swapped in later
- The current implementation is suitable for learning and testing, not a full production-ready DBMS

## Roadmap

The project is being built in stages:

1. Storage foundation
2. Buffer pool and replacement policy
3. Records, tuples, and tables
4. Catalog and schema work
5. Query execution and SQL parsing
6. Indexes and optimization
7. Transactions and recovery
