# 6. Page abstraction

Page size was initially discussed as 4096 bytes, but the project
decision was changed to:

``` cpp
constexpr std::size_t PAGE_SIZE = 8192;
```

This is a deliberate choice and should remain consistent throughout the
project.

The conceptual storage layout is:

``` text
database.db

Page 0 → bytes 0–8191
Page 1 → bytes 8192–16383
Page 2 → bytes 16384–24575
...
```

The important invariant:

``` text
file offset = page_id * PAGE_SIZE
```

Do not hardcode `4096` or `8192` elsewhere. Always use `PAGE_SIZE`.

------------------------------------------------------------------------

## 7. Current `page.hpp`

The intended implementation is:

``` cpp
#pragma once

#include <array>
#include <cstddef>
#include <cstdint>

namespace minidb {

constexpr std::size_t PAGE_SIZE = 8192;

using page_id_t = std::uint32_t;

class Page {
public:
    Page();

    std::byte* data();
    const std::byte* data() const;

    void reset();

private:
    std::array<std::byte, PAGE_SIZE> data_;
};

} // namespace minidb
```

------------------------------------------------------------------------

## 8. Current `page.cpp`

Intended implementation:

``` cpp
#include "minidb/storage/page.hpp"

namespace minidb {

Page::Page() {
    reset();
}

std::byte* Page::data() {
    return data_.data();
}

const std::byte* Page::data() const {
    return data_.data();
}

void Page::reset() {
    data_.fill(std::byte{0});
}

} // namespace minidb
```

### Design reasoning

`Page` is deliberately very simple.

It represents a fixed-size block of raw storage:

``` text
Page
┌──────────────────────────────┐
│          8192 bytes          │
└──────────────────────────────┘
```

`std::byte` is used because the contents are raw bytes rather than text.

The `data()` overloads provide mutable and read-only access.

# 9. DiskManager API

The intended header is:

``` cpp
#pragma once

#include "minidb/storage/page.hpp"

#include <fstream>
#include <string>

namespace minidb {

class DiskManager {
public:
    explicit DiskManager(const std::string& filename);

    ~DiskManager();

    void readPage(page_id_t page_id, Page& page);

    void writePage(page_id_t page_id, const Page& page);

    page_id_t allocatePage();

private:
    std::fstream file_;
    page_id_t next_page_id_{0};
};

} // namespace minidb
```

### Important C++ concepts already discussed

#### `Page&` in `readPage`

``` cpp
void readPage(page_id_t page_id, Page& page);
```

The caller supplies a `Page`, and the DiskManager fills it.

This avoids returning/copying a 8192-byte Page object.

Example:

``` cpp
Page page;
disk.readPage(5, page);
```

#### `const Page&` in `writePage`

``` cpp
void writePage(page_id_t page_id, const Page& page);
```

The DiskManager only reads from the supplied Page in order to write it
to disk, so it should not modify it.

`const` communicates that guarantee.

#### `private`

The user of `DiskManager` should only need to know its public API:

``` text
readPage()
writePage()
allocatePage()
```

Implementation details such as:

``` cpp
std::fstream file_;
page_id_t next_page_id_;
```

remain private.

# 10. DiskManager implementation discussed

The intended first implementation is:

``` cpp
#include "minidb/storage/disk_manager.hpp"

#include <stdexcept>

namespace minidb {

DiskManager::DiskManager(const std::string& filename) {
    file_.open(
        filename,
        std::ios::in |
        std::ios::out |
        std::ios::binary
    );

    // File does not exist -> create it
    if (!file_) {
        file_.clear();

        file_.open(
            filename,
            std::ios::out |
            std::ios::binary
        );

        file_.close();

        file_.open(
            filename,
            std::ios::in |
            std::ios::out |
            std::ios::binary
        );
    }

    if (!file_) {
        throw std::runtime_error(
            "Could not open database file"
        );
    }

    file_.seekg(0, std::ios::end);

    const auto size = file_.tellg();

    next_page_id_ =
        static_cast<page_id_t>(
            size / PAGE_SIZE
        );
}

DiskManager::~DiskManager() {
    if (file_.is_open()) {
        file_.close();
    }
}

void DiskManager::readPage(
    page_id_t page_id,
    Page& page
) {
    const auto offset =
        static_cast<std::streamoff>(
            page_id * PAGE_SIZE
        );

    file_.seekg(offset);

    file_.read(
        reinterpret_cast<char*>(page.data()),
        PAGE_SIZE
    );
}

void DiskManager::writePage(
    page_id_t page_id,
    const Page& page
) {
    const auto offset =
        static_cast<std::streamoff>(
            page_id * PAGE_SIZE
        );

    file_.seekp(offset);

    file_.write(
        reinterpret_cast<const char*>(page.data()),
        PAGE_SIZE
    );

    file_.flush();
}

page_id_t DiskManager::allocatePage() {
    return next_page_id_++;
}

} // namespace minidb
```

### Important note

This is a **first educational implementation**, not production-quality
storage code yet.

Potential future improvements include:

-   validating `page_id`
-   checking `read()` / `write()` failures
-   ensuring file size is page-aligned
-   explicit file creation helper
-   synchronization/thread safety
-   free-page management
-   metadata
-   WAL/recovery

Do not overengineer these yet.

# 11. `fstream` behavior discussed

The constructor first tries:

``` cpp
file_.open(
    filename,
    std::ios::in |
    std::ios::out |
    std::ios::binary
);
```

If the database file does not exist, this fails because `in | out` does
not create a missing file.

Then:

``` cpp
if (!file_)
```

checks the stream's failure state.

`file_.clear()` clears the error flags.

Then:

``` cpp
file_.open(
    filename,
    std::ios::out |
    std::ios::binary
);
```

creates the file.

After that it is closed and reopened in normal read/write mode.

Reasoning:

``` text
in + out
→ open existing DB

out
→ create missing DB

in + out
→ use DB normally
```

`std::ios::in` is intentionally not used in the creation step because a
missing file opened for input does not get created.

# 12. Destructor / `~DiskManager()`

C++ destructor syntax:

``` cpp
~DiskManager()
```

means the destructor.

The DiskManager owns an open file stream, so its lifetime controls the
resource.

Example:

``` cpp
{
    DiskManager disk("database.db");

    // use database
} // ~DiskManager() runs automatically
```

The project is using the C++ RAII idea:

> Resource lifetime is tied to object lifetime.
